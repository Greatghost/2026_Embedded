## 一、整体架构

### 1.1 三段通信链路

```
┌──────────┐   USB CDC    ┌──────────┐   CAN1/CAN2   ┌──────────┐   UART4    ┌──────────┐
│  上位机   │ ───────────▶ │  云台板   │ ───────────▶ │  底盘板   │ ─────────▶│ 裁判系统  │
│ (NUC/PC)  │ ◀─────────── │ (STM32F4)│ ◀─────────── │ (STM32F4)│ ◀─────────│ (V2.0.0) │
└──────────┘              └──────────┘              └──────────┘           └──────────┘
                              │   CAN1/CAN2
                              ▼
                         ┌──────────┐
                         │  云台电机 │
                         │  (DM/3508)│
                         └──────────┘
                              │   CAN1
                              ▼
                         ┌──────────┐
                         │  底盘电机 │
                         │ (3508/6020)│
                         └──────────┘
```

### 1.2 各段协议概览

| 段 | 物理层 | 协议 | 帧类型数 | 关键文件 |
|---|---|---|---|---|
| 上位机↔云台 | USB CDC 虚拟串口 | 自定义 0x21 帧头 | 上行 12 / 下行 6 | `Gimbal/application/src/pc_serial.c` |
| 云台↔底盘 | CAN 1Mbps | 标准 CAN 2.0A 8B 帧 | 21 | `Gimbal/bsp/boards/src/bsp_can.c`、`Chassis/User/src/app/GimbalSend.c` |
| 底盘↔裁判 | UART4 115200 + DMA | 0xA5 帧头 + cmd_id | 18 cmd_id | `Chassis/User/src/peripheral/Referee.c`、`Chassis/Mylib/src/bsp_referee.c` |

### 1.3 数据流总览

```
裁判系统
  │ 0x0001/0x0003/0x0201~0x020D/0x0301/0x0303 (UART4)
  ▼
[Referee.c 解包] → referee_data 全局
  │
  ├─ [裁判→上位机] JudgeDataCanSend → CAN2 0x094~0x0A3 → 云台 ChassisGet.c → pc_serial.c 上行帧 → USB CDC
  ├─ [裁判→裁判] Send_DecisionPack (0x0301/0x0120)
  ├─ [上位机→裁判] 0x02/0x03 下行 → USB → 0x152/0x153 CAN 分段 → 底盘 → 0x0307/0x0308 UART4
  └─ [裁判→底盘本地] chassis_power_limit, buffer_energy → ChasisControlTask/PowerControlTask
```

## 三、上位机 ↔ 云台板（USB CDC）

### 3.1 上行帧（云台→上位机）

所有上行帧统一 **15 字节** 长度，布局固定：

```
+--------+----------+----------------+--------+
| byte 0 | byte 1   | byte 2 .. 13  | byte 14|
+--------+----------+----------------+--------+
|  0x21  | TypeID   |  12B Data     |  CRC8  |
+--------+----------+----------------+--------+
```

- 帧头固定 `'!'` (0x21)
- TypeID 区分 12 种数据包
- CRC8：poly=`0x31`，init=`0xFF`，非反射，覆盖 byte 0~13
- 共享单缓冲 `SendToPC_Buff[15]`，TxState 检查避免覆盖
- 编译期尺寸断言：`typedef char ...SizeCheck[(sizeof(...) == N) ? 1 : -1]`（`pc_serial.h:431-437`）

#### 3.1.1 TypeID 枚举

#### 3.1.4 SendtoPC 调度与 TxState 管理（`pc_serial.c:770-842`）

```c
void SendtoPC(uint8_t data_type)
{
    // (1) TypeID 10 新鲜度闸门：1500ms 内须有 CAN 0x09F + 0x0A3 更新
    if (data_type == JUDGE_PC_DATA_SENTRY_DURATION &&
        SentryDurationDataIsFresh() == 0U) return;

    // (2) TxState 忙时直接丢弃当前帧，避免覆盖正在 DMA 传输的 SendToPC_Buff
    USBD_CDC_HandleTypeDef *hcdc = (USBD_CDC_HandleTypeDef *)hUsbDeviceFS.pClassData;
    if (hcdc != NULL && hcdc->TxState != 0U) {
        usb_cdc_busy_count++;
        return;
    }

    // (3) 根据 data_type 选择对应的 Pack 函数，全部写入共享 SendToPC_Buff
    // ... switch 分支调用 SendtoPCPack / Send2PCJudge / SendtoPCBlood_1 ...

    // (4) 调用 CDC_Transmit_FS 发送
    uint8_t tx_ret = CDC_Transmit_FS(SendToPC_Buff, PC_SENDBUF_SIZE);
    if (tx_ret == USBD_BUSY) usb_cdc_busy_count++;
}
```

关键点：
- **单缓冲** `SendToPC_Buff[15]` 被所有 TypeID 共享，TxState 忙时直接 return 不覆盖
- **不主动重试**，丢帧累加 `usb_cdc_busy_count`
- **看门狗** `CDC_Transmit_FS_Watchdog(100U)` 在 `GimbalTask.c:741` 每 2ms 调用一次

### 3.2 下行帧（上位机→云台）

下行帧**长度不固定**，由 byte 1 的 `DownlinkTypeID` 决定。所有下行帧 byte 0 都是 `0x21`。

#### 3.2.1 DownlinkTypeID 枚举

```c
#define PC_DOWNLINK_CONTROL      0x00  // GimbalControlFrame 13B
#define PC_DOWNLINK_SENTRY_CMD   0x01  // SentryCommandFrame 6B
#define PC_DOWNLINK_MAP_PATH     0x02  // MapPathFragment 64B (分片)
#define PC_DOWNLINK_CUSTOM_INFO  0x03  // CustomInfoFrame 36B
#define PC_DOWNLINK_COORD        0x04  // SentryCoordinateFrame 17B
#define PC_DOWNLINK_TRAJECTORY   0x05  // GimbalTrajectoryFrame 26B (MPC)
#define PC_CONTROL_TIMEOUT_MS    200U
```

#### 3.2.2 下行帧总表

| TypeID | 名称 | 总长 | 内容与去向 |
|---|---|---|---|
| 0x00 | `GimbalControlFrame` | 13B | 控制帧：底盘速度+角度+FireCode，写入 `pc_control_shadow`，**不转发 CAN** |
| 0x01 | `SentryCommandFrame` | 6B | 哨兵命令字 → `Can1SendSentryCmd` 转发 CAN 0x15A |
| 0x02 | `MapPathFragment` | 64B×2 | 64B 分片 ×2，`MapPath_OnFragment` 重组 105B → `Can1SendMapPath` 转发 CAN 0x152 分 15 帧 |
| 0x03 | `CustomInfoFrame` | 36B | 0x0308 custom_info_t 原样 34B → `Can1SendCustomInfo` 转发 CAN 0x153 分 5 帧 |
| 0x04 | `SentryCoordinateFrame` | 17B | 哨兵坐标 x/y cm，写入 `sentry_position_x/y_cm`，**不转发 CAN**（仅本地缓存，ChassisTask 周期性发 CAN 0x151） |
| 0x05 | `GimbalTrajectoryFrame` | 26B | MPC 轨迹：6×float，写入 `pc_control_shadow`，**不转发 CAN** |

> 0x02 因 USB FS 单包 64B 限制，原 107B MapPathFrame 拆为两个固定 64B 物理分片下发。

#### 3.2.3 字节流拆包/粘包（`pc_serial.c:976-1066 PCStreamReceive`）

USB CDC 是字节流，该函数负责拆包/粘包：

1. **帧头搜索**：只有收到 `'!'` 才开始入缓冲
2. **变长期望**：第二字节（type_id）决定整帧长度
3. **粘包处理**：循环逐字节处理，一帧完成后立即开始下一帧
4. **半帧超时**：20ms 内未补齐整帧则丢弃
5. **NULL 复位**：传入 `NULL` 强制重置状态机（被 `PCStreamProcessPending` 在溢出后调用）

```c
static unsigned char frame_buffer[PC_RECVBUF_SIZE];  // 64B
// ...
switch (byte) {
    case PC_DOWNLINK_CONTROL:    expected_length = sizeof(GimbalControlFrame_t);    break; // 13
    case PC_DOWNLINK_SENTRY_CMD: expected_length = sizeof(SentryCommandFrame_t);   break; // 6
    case PC_DOWNLINK_MAP_PATH:   expected_length = sizeof(MapPathFragment_t);      break; // 64
    case PC_DOWNLINK_CUSTOM_INFO:expected_length = sizeof(CustomInfoFrame_t);      break; // 36
    case PC_DOWNLINK_COORD:      expected_length = sizeof(SentryCoordinateFrame_t);break; // 17
```

#### 3.2.5 MapPath_OnFragment 双分片重组（`pc_serial.c:845-974`）

状态机结构（`pc_serial.h:215-221`）：

```c
typedef struct {
    uint8_t  active;            // 是否有 pending 路径
    uint8_t  sequence;          // 当前 pending 的 sequence
    uint8_t  has_fragment[2];   // [0]=首段已收, [1]=尾段已收
    uint8_t  payload[MAP_PATH_PAYLOAD_SIZE];  // 重组 buffer 105B
    uint32_t started_ms;        // 首段到达时间
} map_path_pending_t;
```

重组流程：

```
fragment 0 (56B payload) → 重组 buffer [0..55]
fragment 1 (49B payload) → 重组 buffer [56..104]
重组后 105B = 0x0307 map_data_t 原始 payload
```

校验：
- `head == 0x21`、`type_id == 0x02`、`fragment_count == 2`、`fragment_index <= 1`
- `payload_length` 严格匹配：index 0 = 56，index 1 = 49
- CRC16（reflected 0x1021，CRC-16/X-25）校验 byte 0-61
- 重组超时 100ms
- `payload[0]`（intention）必须为 1/2/3

诊断计数器 `g_map_path_rx_debug`：7 个 uint32 + 2 个 uint8（`pc_serial.h:200-210`）

### 3.3 PCControlSnapshot 原子快照（奇偶序列锁）

#### 3.3.1 Shadow 结构（`pc_serial.h:461-477`）

```c

    float yaw_omega, pitch_omega, yaw_alpha, pitch_alpha;

    uint8_t shoot_state, cap_state;
    uint8_t follow_mode, aim_mode, rotate_state;
```

#### 3.3.2 写入侧（PCReceive 0x00/0x05 分支）

```c
pc_control_sequence++;       // 奇数：写入中
__DMB();
/* 写入 pc_control_shadow 各字段 */
__DMB();
pc_control_sequence++;       // 偶数：写入完成
```

#### 3.3.3 读取侧 PCControlGetSnapshot（`pc_serial.c:312-351`）

```c
uint8_t PCControlGetSnapshot(PCControlSnapshot_t *snapshot) {
    for (;;) {
        sequence_start = pc_control_sequence;
        if ((sequence_start & 1U) != 0U) continue;  // 写入中，重试
        __DMB();
        *snapshot = pc_control_shadow;
        last_rx_tick = pc_control_last_rx_tick;
        received = pc_control_received;
        __DMB();
        sequence_end = pc_control_sequence;
        if (sequence_start == sequence_end && (sequence_end & 1U) == 0U) break;
    }
    if (received == 0U) return 0U;
    return ((HAL_GetTick() - last_rx_tick) <= PC_CONTROL_TIMEOUT_MS) ? 1U : 0U;
}
```

经典奇偶序列锁（seqlock）：读到奇数重试，读到偶数但前后 sequence 不一致也重试。超时 200ms。

API：
- `PCControlGetSnapshot(snapshot)` —— 返回 1=在线且快照有效，0=离线
- `PCControlIsOnline()` —— 仅返回在线状态

#### 4.2.1 通用发送原语 CanSend（云台侧 `bsp_can.c:376-421`）

#### 4.2.3 Can1SendMapPath + Can1ServiceMapPathTx（`bsp_can.c:440-558`）

**生产者-消费者快照机制**（关键设计）：
- `map_path_staged_payload`：单写者（USB CDC 任务）发布的最新快照

- `Can1ServiceMapPathTx`：ChassisTask 1ms 周期调用，逐帧发送

### 4.5 底盘侧 0x152/0x153 分段重组（`GimbalReceive.c`）

#### 4.5.1 0x152 MapPath 分段重组状态机

参数（`GimbalReceive.h:83-86`）：
- `MAP_PATH_PAYLOAD_SIZE = 105`
- `MAP_PATH_SEGMENT_COUNT = 15`
- `MAP_PATH_SEGMENT_PAYLOAD = 7`
- `MAP_PATH_TIMEOUT_MS = 50`

状态机流程：
1. seg >= 15 → invalid_segment_count++，清空 pending，返回
2. seg == 0 / 14 → segment0/14_rx_count++
3. **超时检查**：`now_ms - started_ms > 50ms` → timeout_count++，清空 pending
4. **seg == 0**：清空 pending，启动新 pending，拷贝首 7B，返回
5. **乱序/无起始**：order_drop_count++，清空 pending，返回
6. **顺序到达**：拷贝 7B，next_index++
7. **重组完成**（next_index == 15）：
   - 校验 `intention = payload[0]`，必须 ∈ {1,2,3}
   - 若 `map_data_ready` 仍为 1 → ready_overwrite_count++
   - `memcpy` 到 `map_data_payload[105]`，置 `map_data_ready = 1`

⭐ **不在 ISR 中调用 `Referee_SendMapData0x0307`，避免阻塞**（`GimbalReceive.c:166-168` 注释明确）

#### 4.5.2 MapPath_TakeReady（`GimbalReceive.c:191-219`）

```c
primask = __get_PRIMASK();
__disable_irq();        // 全局关中断（CAN2 RX 使用最高优先级中断，FreeRTOS 临界区不够）
if (map_data_ready != 0U) {
    memcpy(out_payload_105, map_data_payload, 105);
    map_data_ready = 0U;
    has_payload = 1U;
    ready_taken_count++;
}
__DMB();
if (primask == 0U) __enable_irq();
```

⭐ **关键约束**：CAN2 RX 使用最高优先级中断（抢占优先级 0），FreeRTOS 的 `taskENTER_CRITICAL` 不能保证屏蔽它，所以用 `__disable_irq` + PRIMASK 保存恢复。

#### 4.5.3 0x153 CustomInfo 分段重组

参数（`GimbalReceive.h:139-142`）：
- `CUSTOM_INFO_PAYLOAD_SIZE = 34`
- `CUSTOM_INFO_SEGMENT_COUNT = 5`
- `CUSTOM_INFO_SEGMENT_PAYLOAD = 7`（最后一帧仅 6B 有效）
- `CUSTOM_INFO_TIMEOUT_MS = 50`

机制与 MapPath 类似，最后一帧 seg==4 时拷贝长度 = `34 - 4*7 = 6B`。

### 4.6 CAN ISR 与任务协作

#### 4.6.1 ISR 中的阻塞操作审计

**云台侧 CAN ISR**：6 个 ISR（`stm32f4xx_it.c:221-342`）只调用 `HAL_CAN_IRQHandler`，无 DMA 等待、无邮箱忙等待、无业务逻辑。接收回调 `HAL_CAN_RxFifo0/1MsgPendingCallback` 只做 `HAL_CAN_GetRxMessage` + 清标志 + `MotorReceive`，**无任何阻塞调用**。

## 五、底盘板 ↔ 裁判系统（UART4）

### 5.1 帧格式

```
┌──────┬──────────┬─────┬──────┬──────────┬────────┐
│ SOF  │data_len  │ seq │ CRC8 │   data   │ CRC16  │
│ 0xA5 │ (2bytes) │ 1B  │  1B  │ N bytes  │  2B    │
└──────┴──────────┴─────┴──────┴──────────┴────────┘
```

- **SOF**：帧头起始符，固定 `0xA5`
- **data_length**：数据段长度（不含帧头 5 字节和 CRC16），小端序
- **seq**：帧序列号，0-255 循环
- **CRC8**：帧头校验（对前 4 字节）
- **CRC16**：整帧校验（对除 CRC16 外的所有字节）

### 5.2 6 步解析状态机（`Referee.c:200-309`）

```
STEP_HEADER_SOF (搜0xA5)
    │
    ▼
STEP_LENGTH_LOW (读长度低字节)
    │
    ▼
STEP_LENGTH_HIGH (读长度高字节，校验合法性 < 119)
    │
    ▼
STEP_FRAME_SEQ (读帧序列号)
    │
    ▼
STEP_HEADER_CRC8 (读CRC8，校验帧头)
    │ CRC8通过
    ▼
STEP_DATA_CRC16 (读数据域+CRC16，校验整帧)
    │ CRC16通过
    ▼
Referee_SolveFifoData() → 按cmd_id分发
```

前置的圈数保护逻辑（`Referee.c:170-188`）：
- 若 `receive_data_len < decode_data_len`：圈数回卷，重置状态机
- 若 `receive_data_len - decode_data_len > REFEREE_RECVBUF_SIZE`：已落后超过一整圈，丢弃到只剩最后一圈，`dma_overrun_count++`

#### 5.7.3 REFEREE_SendBytes 实现（`bsp_referee.c:119-142`）

```c
void REFEREE_SendBytes(uint8_t *data, uint8_t len) {
    if (data == NULL || len == 0U || len > REFEREE_SENDBUF_SIZE) return;
    for (;;) {
        taskENTER_CRITICAL();                                      // 临界区
        if (DMA_GetCmdStatus(REFEREE_SEND_DMAx_Streamx) == DISABLE) {
            memcpy(SendToReferee_Buff, data, len);                // 拷贝到发送缓冲
            DMA_SetCurrDataCounter(REFEREE_SEND_DMAx_Streamx, len);
            DMA_Cmd(REFEREE_SEND_DMAx_Streamx, ENABLE);           // 启动 DMA
            taskEXIT_CRITICAL();
            return;
        }
        taskEXIT_CRITICAL();
        vTaskDelay(pdMS_TO_TICKS(1U));                              // DMA 忙则让出 CPU 1ms
    }
}
```

要点：检查-and-启动作为一个任务级原子事务；DMA 忙时 yield 而非空转整帧串口时间；长度上限 `REFEREE_SENDBUF_SIZE=128`。

#### 5.7.4 DMA 圈数无锁读取（`Referee.c:136-164`）

```c
primask = __get_PRIMASK();
__disable_irq();
wraps = referee_data.decoder.judgementFullCount;
remaining = DMA_GetCurrDataCounter(REFEREE_RECV_DMAx_Streamx);
if (DMA_GetFlagStatus(..., TCIFx) != RESET) {   // 处理 TC 还没来得及 ISR 的窗口
    wraps++;
    remaining = DMA_GetCurrDataCounter(...);
}
__DMB();
if (primask == 0U) __enable_irq();
return (uint64_t)wraps * REFEREE_RECVBUF_SIZE + (uint64_t)(REFEREE_RECVBUF_SIZE - remaining);
```

返回 64bit 累计字节数，避免 32bit 回零问题。

### 6.1 USB CDC TxState 看门狗四步恢复（`usbd_cdc_if.c:337-401`）

⭐ **关键修复**：上位机停止读取后 TxState 卡死，仅清 TxState 不够，必须四步全部执行。

```c
void CDC_Transmit_FS_Watchdog(uint32_t timeout_ms) {
    static uint32_t stuck_start_tick = 0U;
    // ... 检查 dev_state、TxState ...
    if (hcdc->TxState != 0U) {
        if (stuck_start_tick == 0U) stuck_start_tick = HAL_GetTick();
        else if ((HAL_GetTick() - stuck_start_tick) > timeout_ms) {
            // 四步恢复
            hcdc->TxState = 0U;                                        // (1) 清 TxState 软件标志
            HAL_PCD_EP_Flush(hpcd, CDC_IN_EP);                        // (2) 清空 TX FIFO
            USBx_INEP(epnum)->DIEPINT = 0xFFFFFFFFU;                  // (3) 清 DIEPINT 挂起的中断标志
            hpcd->IN_ep[epnum].xfer_len = 0U;                         // (4) 清 HAL 软件层 IN_ep 状态
            hpcd->IN_ep[epnum].xfer_buff = NULL;
            hpcd->IN_ep[epnum].xfer_count = 0U;
            usb_cdc_tx_reset_count++;
            stuck_start_tick = 0U;
        }
    }
}
```

要点：
- `USBx_BASE` 是 HAL 内部 `USBx_INEP()` 宏依赖的局部变量，必须按 HAL 同样的方式赋值
- 通过 `CDC_IN_EP & 0x7F` 取端点号（屏蔽方向位）
- 只清 TxState 不够：TX FIFO 残留数据会导致上位机重新读取时帧错位（表现为"收不到数据"）

### 6.2 单缓冲 SendToPC_Buff 的共享风险

`SendToPC_Buff[15]` 被所有 TypeID 共享。`SendtoPC` 在 Pack 前检查 `TxState != 0`，若忙直接 return 不覆盖。这是"避免上行帧发送冲突"的简化方案，不操作 USB 寄存器。

⭐ **`UserTxBufferFS[2048]` 实际未被使用**：`CDC_Transmit_FS` 调用时传入的 `Buf` 实际上是 `SendToPC_Buff`（应用层缓冲）。`USBD_CDC_SetTxBuffer(&hUsbDeviceFS, Buf, Len)` 会把 TX 缓冲指针临时改写为 `SendToPC_Buff`。如果 TxState 看门狗没有及时清状态，前一帧 DMA 还在传输 `SendToPC_Buff`，后一帧 pack 会覆盖同一缓冲导致上位机收到错位数据。`SendtoPC` 中的 `TxState != 0` 检查正是为了规避这一风险。

### 6.3 SPSC 环形缓冲（下行 USB CDC 接收）

USB OUT 中断只拷贝到 512B 环形缓冲，解析/CRC/CAN 转发全部推迟到任务上下文：

```
USB OUT 中断 → CDC_Receive_FS → PCStreamEnqueueFromISR（仅拷贝）
                                      │
                                      ▼
                              pc_rx_ring[512] (SPSC)
                                      │
                                      ▼
                          PCStreamProcessPending (任务上下文)
                                      │
                                      ▼
                              PCStreamReceive (拆包) → PCReceive (分发)
```

`pc_rx_ring_overflow` 时不部分入队，整包丢弃并复位拆包状态机。

### 6.4 奇偶序列锁（PCControlSnapshot）

写入 `pc_control_shadow` 时 `sequence++` → 写 → `sequence++`（奇→偶），读取侧循环读到偶数且前后一致才返回。避免控制任务读到半更新的 shadow。

### 6.5 新鲜度闸门

- TypeID 10 在 `SendtoPC` 入口先检查 `SentryDurationDataIsFresh`（1500ms 内有 CAN 0x09F + 0x0A3 更新）
- 下行 0x00 在 `PCControlGetSnapshot` 出口检查 200ms 超时（`PC_CONTROL_TIMEOUT_MS`）

```c
#define SENTRY_DURATION_FRESH_MS 1500U
static uint8_t SentryDurationDataIsFresh(void) {
    const uint32_t now = HAL_GetTick();
    if (sentry_duration_last_rx_tick == 0U || outpost_hp_recv.last_rx_tick == 0U) return 0U;
    if ((now - sentry_duration_last_rx_tick) > 1500U ||
        (now - outpost_hp_recv.last_rx_tick) > 1500U) return 0U;
    return 1U;
}
```

### 6.6 MapPath/CustomInfo 双缓冲 + generation 计数

- `map_path_staged_payload`：单写者（USB CDC 任务）发布的最新快照
- `map_path_staged_generation`：奇数表示拷贝进行中，偶数表示稳定
- `Can1SendMapPath`：generation+1 → `__DMB()` → memcpy → `__DMB()` → generation+2
- `MapPathLoadLatestSnapshot`：任务侧用前后两次 generation 校验避免撕裂

### 6.7 CAN ISR 不阻塞

**云台侧**：6 个 CAN ISR 只调用 `HAL_CAN_IRQHandler`，无 DMA 等待、无邮箱忙等待。`MotorReceive` 内全部是 `memcpy`（固定 8B，O(1)）、位域解包、`HAL_GetTick()`、`LossUpdate`。

**底盘侧**：CAN ISR 位于 `can1.c` / `can2.c`（**不在 `stm32f4xx_it.c`**，该文件仅保留模板注释）。`CanReceiveAll` 纯内存操作，无 UART/DMA 调用。

### 6.8 flag + 任务模式（0x0307/0x0308 转发）

```
云台 → 0x152 CAN帧 (15帧) → CAN2_RX1_IRQHandler (底盘)
   → CanReceiveAll → MapPath_OnCanReceive (状态机)
   → 105B 重组完成 → map_data_ready=1 (volatile)
   ↑ ISR 结束

Refereetask (任务上下文):
   → MapPath_TakeReady(out_105) [__disable_irq 临界区]
   → Referee_SendMapData0x0307(out_105)  → UART4 → 裁判系统
```

⭐ **关键约束**：CAN2 RX 使用最高优先级中断（抢占优先级 0），FreeRTOS 的 `taskENTER_CRITICAL` 不能保证屏蔽它，所以用 `__disable_irq` + PRIMASK 保存恢复。

### 6.9 0x0303 memcmp 去重

裁判系统可能重复下发相同指令。底盘 Referee 层收到 `0x0303` 时进行 `memcmp` 二进制比较，只有内容变化时才更新数据并置 `is_robot_command_update` 标志。`JudgeDataCanSend()` 检测标志后发送一帧，并清零标志。

### 6.10 0x0307/0x0308 sender_id 强制覆盖

⭐ **设计要点**：`frame[110..111]`（map_data_t.sender_id）和 `frame[7..8]`（custom_info_t.sender_id）在 `Referee_SendMapData0x0307`/`0x0308` 内部用裁判 0x0201 的 `robot_id` 强制覆盖，作为唯一可信源——防止上位机默认 0 或红蓝方配置错误。

- **影响**：云台侧已配置 0x0A1/0x0A2/0x0A3 的滤波器与解码逻辑（`bsp_can.c` Bank 4 + `ChassisGet.c`），但底盘根本不发送这些帧 → 上位机TypeID 6（Extended，依赖 0x0A2）和 TypeID 10（SentryDuration，依赖 0x0A3）的对应字段会持续为 0
- **建议**：在 `JudgeDataCanSend` 中按 10Hz/1Hz 节拍补齐这三个发送调用

#### 9.2.5 H-new2: NIUNIU / QI_TIAN_DA_SHENG 配置缺失 0x152/0x153 CAN 滤波器（`Chassis/User/inc/config/can_config.h`）

- **现状**：TIGER 机型 `CAN2_FIFO1_ID2=0x153`、`CAN2_FIFO1_ID3=0x152` 正确接收 MapPath/CustomInfo 分段；但 NIUNIU 和 QI_TIAN_DA_SHENG 机型 `CAN2_FIFO1_ID2=0x002`（重复）、`CAN2_FIFO1_ID3=0x001`
- **影响**：若使用 NIUNIU/QI_TIAN_DA_SHENG 编译，0x152/0x153 转发链路完全失效
- **建议**：统一三个机型的 CAN2 FIFO1 ID 配置

#### 9.2.6 H-new3: JudgeBloodData_ForSend1_t 实际仅 4B，CAN DLC=8（`GimbalSend.h:48-58`）

- **现状**：位域总计 32 bit = 4 字节，但 `memcpy(tx_message.Data, Blood2Send1, sizeof(JudgeBloodData_ForSend1_t))` 只拷贝 4B，剩余 4B 为栈上未初始化数据
- **影响**：CAN 帧 byte 4-7 内容不确定，云台侧 `memcpy(&JudgeBlood_F, data, 8)` 会读到脏数据
- **建议**：在 `JudgeBloodData_ForSend1_t` 末尾添加 4B 显式 `reserved[4]` 占位，或在发送前 `memset(tx_message.Data, 0, 8)`

#### 9.2.7 H-new4: TypeID 4 RFIDAndBuff 的 rfid_status 字段类型不一致（`pc_serial.h:312-321`）

- **现状**：结构体声明 `uint32_t rfid_status`（4B），但整体被 `RFIDAndBuffSizeCheck` 静态断言约束为 15B，`Append_CRC8_Check_Sum` 使用 `PC_SEND_BLOOD_SIZE = 15`
- **影响**：`rfid_status` 实际仅 2B 进入上行帧（`#pragma pack(1)` 下位域压缩或截断），与 0x0209 的 4B 语义不匹配
- **建议**：将 `rfid_status` 字段改为 `uint16_t` 或调整结构体布局明确 2B 装入

### 9.3 工程约定（来自 `project_memory.md`）
