# 机器人与裁判系统通信架构解析

> 基于 RoboMaster 裁判系统串口协议 V2.0.0（2026-07-13 更新），适用于哨兵机器人（Sentry）

---

## 一、整体架构概览

通信代码分为 **四层**：

| 层级 | 文件 | 职责 |
|------|------|------|
| 硬件抽象层 | `Mylib/src/bsp_referee.c` `Mylib/inc/bsp_referee.h` | STM32 UART4 + DMA 物理通信 |
| 协议定义层 | `User/inc/tools/protocol.h` | 帧格式、命令ID枚举、解析状态机 |
| 数据层（核心） | `User/src/peripheral/Referee.c` `User/inc/peripheral/Referee.h` | 数据解析分发、结构体定义、UI绘制 |
| 任务层 | `Task/src/RefereeTask.c` `Task/inc/RefereeTask.h` | FreeRTOS 任务，哨兵决策上报 |

## 二、硬件抽象层 — bsp_referee

### 硬件配置

- **串口**：UART4（PC10/PC11），波特率 **115200**
- **接收DMA**：DMA1_Stream2，**环形缓冲区**模式，缓冲区 4096 字节
- **发送DMA**：DMA1_Stream4，普通模式，缓冲区 128 字节

### 数据流向

```
裁判系统 ──UART4──> [DMA环形缓冲 Refereebuffer[4096]] ──> 软件解析
裁判系统 <──UART4── [DMA发送 SendToReferee_Buff[128]] <── 软件打包
```

### 关键函数

| 函数 | 功能 |
|------|------|
| `REFEREE_Configuration()` | 初始化UART4 GPIO、USART、DMA接收(环形)和发送 |
| `REFEREE_SendBytes(data, len)` | **临界区保护**（`taskENTER_CRITICAL`/`taskEXIT_CRITICAL`）下检查 DMA 状态 → `memcpy` 到 `SendToReferee_Buff` → 启动 DMA；DMA 忙时 `vTaskDelay(1ms)` 让出 CPU（不忙等待），避免任务死锁 |
| `REFEREE_RECV_DMAx_Streamx_IRQHandler()` | DMA接收完成中断，`judgementFullCount++` 记录环形缓冲区溢出圈数 |
| `REFEREE_SEND_DMAx_Streamx_IRQHandler()` | DMA发送完成中断，关闭DMA发送流 |

> **约束**（来自 `project_memory.md`）：`REFEREE_SendBytes` 必须使用临界区保护 `memcpy` 和 DMA 启动，避免 ISR 与任务之间的数据竞争；不得使用 `while (DMA_GetCmdStatus)` 忙等待。`MAX_REFEREE_DATA_LEN` 已对齐 `REF_PROTOCOL_FRAME_MAX_SIZE`（128B）。

### 环形缓冲区圈计数机制

DMA配置为环形模式，每次自动转满一圈触发中断。软件通过以下公式计算总接收量：

```
总接收长度 = 4096 - DMA当前剩余计数 + judgementFullCount × 4096
```

## 三、协议定义层 — protocol.h

### 帧格式

```
┌──────┬──────────┬─────┬──────┬──────────┬────────┐
│ SOF  │data_len  │ seq │ CRC8 │   data   │ CRC16  │
│ 0xA5 │ (2bytes) │ 1B  │  1B  │ N bytes  │  2B    │
└──────┴──────────┴─────┴──────┴──────────┴────────┘
```

- **SOF**：帧头起始符，固定 `0xA5`
- **data_length**：数据段长度（不含帧头5字节和CRC16），小端序
- **seq**：帧序列号，0-255循环
- **CRC8**：帧头校验（对前4字节）
- **CRC16**：整帧校验（对除CRC16外的所有字节）

### 解析状态机（6步）

```
STEP_HEADER_SOF (搜0xA5)
    │
    ▼
STEP_LENGTH_LOW (读长度低字节)
    │
    ▼
STEP_LENGTH_HIGH (读长度高字节，校验合法性)
    │
    ▼
STEP_FRAME_SEQ (读帧序列号)
    │
    ▼
STEP_HEADER_CRC8 (读CRC8，校验帧头)
    │ CRC8通过
    ▼
STEP_DATA_CRC16 (读数据域+CRC16，校验整帧)
    │ CRC16通过
    ▼
Referee_SolveFifoData() → 按cmd_id分发
```

## 四、数据层（核心）— Referee.c / Referee.h

### 4.1 全局数据结构 `Referee_t`

所有裁判系统下发数据统一存储在全局结构体 `referee_data` 中：

```c
Referee_t referee_data;  // 全局单例
```

包含三大类数据：

#### 0x000X — 比赛基础数据

| 字段 | 来源cmd_id | 说明 |
|------|-----------|------|
| `Game_Status` | 0x0001 | 比赛类型(4bit)、比赛阶段(4bit)、阶段剩余时间、同步时间戳 |
| `Game_Result` | 0x0002 | 比赛结果（平局/红胜/蓝胜） |
| `Game_Robot_friend_HP` | 0x0003 | 友方1/2/3/4/7号血量、**伤害值差**、前哨站血量、基地血量、**敌方前哨站血量**、**敌方基地血量**（V2.0.0 新增3字段） |

#### 0x010X — 场地事件数据

| 字段 | 来源cmd_id | 说明 |
|------|-----------|------|
| `Event_Data` | 0x0101 | 补给站状态、Buff状态、高地占领、基地护盾、飞镖信息、得分状态 |
| `Dart_Remaining_Time` | 0x0105 | 飞镖发射口剩余时间 |

#### 0x020X — 机器人状态数据

| 字段 | 来源cmd_id | 说明 |
|------|-----------|------|
| `Game_Robot_State` | 0x0201 | 机器人ID、等级、剩余/最大血量、枪管冷却值/上限、底盘功率上限、电源输出状态 |
| `Power_Heat_Data` | 0x0202 | 底盘电压/电流/功率、缓冲能量、3个发射机构冷却热量 |
| `Game_Robot_Pos` | 0x0203 | 机器人坐标 (x, y, z, yaw) |
| `Buff_Musk` | 0x0204 | 恢复/冷却/防御/易伤Buff等级、攻击Buff值、剩余能量 |
| `Robot_Hurt` | 0x0206 | 被击中装甲板类型、伤害类型 |
| `Shoot_Data` | 0x0207 | 弹丸类型、发射机构ID、射速、初速度(m/s) |
| `Bullet_Remaining` | 0x0208 | 17mm/42mm剩余弹量、金币、堡垒储备17mm允许发弹量 |
| `rfid_status` | 0x0209 | RFID状态位（补给区/己方高地/对方高地/能量机关/飞镖区）+ 扩展8bit |
| `ground_robot_position` | 0x020B | 友方6个地面机器人的float坐标 |
| `Sentry_info` | 0x020D | **哨兵专有**：兑换弹量、远程兑换次数、免费/立即复活、复活金币消耗、脱战状态、队伍17mm弹量、姿态、能量机关可激活、**强化姿态标志**、**6种姿态剩余时长（V2.0.0新增）** |

#### 0x030X — 机器人间通信（最重要）

| 字段 | 说明 |
|------|------|
| `Student_Interactive_Header_Data` | 通信头(data_cmd_id + sender_id + receiver_id) |
| `Robot_Interactive_Data` | 雷达位置/血量映射（兼容旧代码） |
| `Robot_Command` | 小地图下发指令（目标坐标+键盘按键+目标ID） |

#### 雷达站数据（通过0x0301承载）

| 字段 | 子data_cmd_id | 说明 |
|------|--------------|------|
| `Radar_Alert_Info` | 0x0201 | 最近敌人车ID + 距离(m) + 象限(0-7) |
| `Radar_Position_Info` | 0x0202 | 哨兵自身 + 6个敌方机器人 float(x,y) 坐标 |
| `Radar_Enemy_HP` | 0x0205 | 5个敌方机器人 uint16 血量 |

### 4.2 数据解析流程

```
DMA环形缓冲区
      │
      ▼
Referee_UnpackFifoData()        ← 逐字节状态机解帧
      │
      ├── 搜0xA5帧头
      ├── 读长度+序列号
      ├── CRC8校验帧头
      └── CRC16校验整帧
            │ 通过
            ▼
Referee_SolveFifoData(frame)    ← 按cmd_id switch分发
      │
      ├── 0x0001-0x0105  →  比赛/场地数据
      ├── 0x0201-0x020D  →  机器人状态数据 (同时置更新标志)
      │
      └── 0x0301 (特殊处理)：
            │
            读 6字节交互头 (data_cmd_id + sender_id + receiver_id)
            │
            判断 receiver_id == 本哨兵ID (红7/蓝107)?
            │ 是
            ├── data_cmd_id=0x0201 → Radar_Alert_Info + 置 ALL_ENEMY_POS 标志
            ├── data_cmd_id=0x0202 → Radar_Position_Info + 同步到 Robot_Interactive_Data.position
            └── data_cmd_id=0x0205 → Radar_Enemy_HP + 同步到 Robot_Interactive_Data.enemy_hp
```

## 五、任务层 — RefereeTask

### FreeRTOS 任务

- **周期**：每 **10ms** 执行一次（`vTaskDelayUntil(&xLastWakeTime, pdMS_TO_TICKS(10))`，100Hz）
- **核心循环**：
  1. 调用 `Referee_UnpackFifoData()` 持续解包 DMA 环形缓冲
  2. **0x0307 map_data 转发**（节流 1Hz）：检查 `map_data_ready` 标志 → `MapPath_TakeReady`（`__disable_irq` + PRIMASK 临界区拷贝 105B）→ `Referee_SendMapData0x0307`（sender_id 强制覆盖为裁判 0x0201 robot_id）→ `REFEREE_SendBytes`
  3. **0x0308 custom_info 转发**（节流 ~3Hz / 334ms）：检查 `custom_info_ready` 标志 → `CustomInfo_TakeReady` → `Referee_SendCustomInfo0x0308`（sender_id 强制覆盖）→ `REFEREE_SendBytes`
  4. 每 50 次（即 **500ms / 2Hz**）检查复活条件并发送哨兵决策（`Send_DecisionPack`）
  5. UI 绘制代码全部注释（`Referee.c` 中实现保留，`RefereeTask.c` 中调用被注释）
  6. `xEventGroupSetBits(xCreatedEventGroup, REFEREE_TASK_BIT)` 喂看门狗

> **关键约束**：0x152/0x153 CAN 帧到达底盘 ISR 时只置 `map_data_ready`/`custom_info_ready` 标志，不在 ISR 中调用 `REFEREE_SendBytes`（否则 UART4 DMA 阻塞导致 CAN FIFO 溢出）。任务上下文通过 `MapPath_TakeReady`/`CustomInfo_TakeReady` 取走数据并完成 UART 发送。

### 哨兵自主决策上报

通过 **0x0301** 通道，子 `data_cmd_id = 0x0120`，发送到服务端 `0x8080`：

```c
// Send_DecisionPack() 函数内部
custom_interactive_header.data_cmd_id = 0x0120;   // 子内容ID
custom_interactive_header.send_ID = robot_id;      // 本机机器人ID
custom_interactive_header.receiver_ID = 0x8080;    // 服务端ID
```

#### 决策数据结构 `Sentry_decision_referee_t`（4B，`Referee.h:217-227`）

| bit | 字段 | 位宽 | 说明 |
|------|------|------|------|
| 0 | `sentry_if_revive` | 1 | 是否允许复活 |
| 1 | `sentry_immediate_revive` | 1 | 是否申请立即复活 |
| 2-12 | `sentry_bullet_claim` | 11 | 申请购买弹丸数量 |
| 13-16 | `sentry_remote_bullet_claim_times` | 4 | 远程兑换弹丸次数 |
| 17-20 | `sentry_remote_HP_claim_times` | 4 | 远程兑换血量次数 |
| 21-23 | `sentry_posture` | 3 | 哨兵姿态：0-未知/1-进攻/2-防御/3-移动/4-强化进攻/5-强化防御/6-强化移动（RM2026 V2.0） |
| 24 | `sentry_confirm_activate_rune` | 1 | 确认使能量机关进入正在激活状态 |
| 25-31 | `reserve` | 7 | 保留位 |

> 总计 32bit = 4 字节，`REFEREE_SIZE_ASSERT(Sentry_decision_referee_t, 4U)` 编译期断言。

#### 当前自动复活逻辑

```c
// 每500ms执行
if (对战中 && 自身血量为0)
    sentry_decision_referee.sentry_if_revive = 1;  // 申请复活
else
    sentry_decision_referee.sentry_if_revive = 0;
```

## 六、完整数据流全景

```
                         ┌─────────────────────────────────┐
                         │         裁判系统 (Referee)        │
                         │  比赛管理 + 数据中转 + UI显示      │
                         └────────┬──────────────┬──────────┘
                                  │ UART4 115200 │
                      ┌───────────┘              └───────────┐
                      ▼ 下行(接收)                           上行(发送) ▼
           ┌──────────────────────┐              ┌──────────────────────┐
           │  DMA1_Stream2 环形   │              │  DMA1_Stream4 普通   │
```

## 八、关键设计要点

1. **DMA环形缓冲 + 圈计数**：解决高速连续接收问题，软件通过 `judgementFullCount × 4096 + DMA剩余计数` 推算总接收量
2. **状态机逐字节解析**：不依赖帧间隔，能从任意位置恢复同步（搜0xA5字节）
3. **双层CRC校验**：CRC8保护帧头（5字节），CRC16保护整帧
4. **0x0301 复用通道**：承载三种数据——雷达站转发数据、UI绘制指令、哨兵决策上报
5. **机器人ID体系**：红方1-9，蓝方101-109，客户端ID = 机器人ID + 256
6. **哨兵复活逻辑**：每500ms检查一次，对战中且血量为0时自动申请复活
7. **数据更新标志**：`referee_data_updater` 通知其他模块哪些数据已刷新（功率/热量）
8. **边界处理**：环形缓冲区约1/3到2/3区间时自动校正圈计数，防止溢出
